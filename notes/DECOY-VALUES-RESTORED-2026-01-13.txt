================================================================================

After 3 failed approaches, ops-log-2026-01-13-05.txt revealed the TRUE root
cause of Phase 3 charging failures:

APPROACH 1: Write Current Setpoint (ops-log-03)
  - REG 501 = 3.3A (setpoint)
  - Result: CP mode ❌

APPROACH 2: Zero-Current, Untouched Sink (ops-log-04)
  - REG 501 = 0.0A (fixed)
  - REG 498/499 = 30.58W/5.10A (RETAINED from previous operations)

APPROACH 3: Explicit Sink Zeroing (ops-log-05)
  - REG 501 = 0.0A
  - REG 498/499 = 0.0W/0.0A (EXPLICITLY ZEROED)
  - Result: CP mode ❌ (STILL FAILED!)

================================================================================
ROOT CAUSE DISCOVERED
================================================================================

Analysis of ops-log-05 Phase 4 discharge (lines 653-669) showed that
Battery_DischargeCapacity() writes non-zero sink values:
  - REG 498 = 30.00W
  - REG 499 = 5.00A
  - REG 502 = 30.00W

Following the code path backwards:
  1. Battery_DischargeCapacity() calls PSB_SetSinkPower/PSB_SetSinkCurrent
  2. Battery_GoToVoltage() ASSUMES decoy values are present (line 142):
     "Using initialization setpoints (10A/100W decoys) and high limits (61.2A/1224W)"
  3. PSB initialization was changed to "minimalist approach" (line 158):
     "SKIPPING sink register writes - letting PSB use defaults"

THE DISCONNECT:
  - Initialization: "minimalist approach" DOES NOT write sink registers
  - Battery functions: ASSUME sink registers contain decoy values (10A/100W)
  - Result: Sink registers have undefined/retained values, not intended decoys

DISCOVERY FROM CODE ANALYSIS:
  psb10000_dll.h defines decoy values:
    #define PSB_SINK_CURRENT_DECOY  10.0    // A (mode selection decoy)
    #define PSB_SINK_POWER_DECOY    100.0   // W (mode selection decoy)

  These were supposed to be written during initialization but the "minimalist
  approach" removed that step, breaking the assumption made by Battery_GoToVoltage().

================================================================================
WHY ZEROING FAILED (ops-log-05)
================================================================================

When we explicitly zeroed sink registers (0.0W/0.0A), we removed ALL non-zero
values from sink registers. The PSB firmware needs SOME non-zero "background
values" for proper mode selection:

PSB Mode Selection Logic (INFERRED):
  1. When output is enabled, PSB examines ALL setpoint registers (498-502)
  2. If sink registers = 0.0 AND battery voltage < target voltage:
     → PSB interprets as "no sink capability configured"
     → Defaults to CP mode as "safe fallback"
  3. If sink registers = MODERATE VALUES (10A/100W):
     → PSB interprets as "sink capability available but not active"
     → Selects CV mode based on voltage register
     → Sink values act as "background parameters"

ANALOGY:
  Sink decoy values are like "capacity declarations" - telling the PSB "I CAN
  sink up to 10A/100W if needed, but right now I'm in CV mode controlling
  voltage." Without these declarations, PSB assumes no sink capability and
  fails to select CV mode properly.

================================================================================
SOLUTION: RESTORE DECOY VALUE APPROACH
================================================================================

Revert to the ORIGINAL design where sink registers contain moderate "decoy
values" (10A/100W) that act as background parameters:

DECOY VALUES = "Mode Selection Parameters"
  - Not operating limits (that's what LIMIT registers are for)
  - Not active setpoints (voltage register controls in CV mode)
  - Background values that allow PSB to make correct mode selection decisions

CONFIGURATION STRATEGY:
  During Initialization (psb10000_queue.c):
    REG 498 (SINK_MODE_POWER) = 100.0 W (decoy)
    REG 499 (SINK_MODE_CURRENT) = 10.0 A (decoy)
    REG 500 (SET_VOLTAGE) = 0.0 V
    REG 501 (SET_CURRENT) = 0.0 A
    REG 502 (SET_POWER_SOURCE) = 0.0 W

  Before Phase 3 Charging (exp_baseline.c):
    RESTORE decoy values (in case they were changed):
      REG 498 = 100.0 W (decoy)
      REG 499 = 10.0 A (decoy)
    Then configure charging:
      REG 9002 (CURRENT_MAX) = 3.3 A (limit)
      REG 9004 (POWER_MAX) = 30 W (limit)
      REG 500 (SET_VOLTAGE) = 4.2 V (control setpoint)

RESULT:
  - PSB sees voltage as primary control (REG 500 = 4.2V)
  - PSB sees sink capability declared (REG 498/499 = 100W/10A decoys)
  - PSB selects CV SOURCE mode correctly
  - Current is limited by REG 9002 (3.3A), not sink registers

================================================================================
WHY THIS SHOULD WORK
================================================================================

The decoy value approach aligns with PSB firmware expectations:

1. FIRMWARE NEEDS CONTEXT:
   - PSB firmware needs to know "what modes are possible"
   - Non-zero sink registers = "sink mode is available if needed"
   - But voltage register controls actual operation

2. MODE SELECTION HIERARCHY:
   - Primary control: REG 500 (voltage) → CV mode
   - Background capability: REG 498/499 (sink decoys) → sink available
   - Operating limits: REG 9002/9004 (current/power max)
   - Result: CV SOURCE mode with proper limiting

3. MATCHES ORIGINAL DESIGN:
   - Commit 428c749 introduced "moderate decoy values"
   - Battery_GoToVoltage() assumes these exist
   - Minimalist approach broke this assumption
   - Restoring decoys fixes the disconnect

4. SYMMETRY WITH DISCHARGE:
   - Discharge operations write actual sink values
   - Charge operations use sink decoys as background
   - PSB firmware distinguishes between "capability" and "active mode"

================================================================================
LESSONS LEARNED
================================================================================

1. UNDERSTAND ORIGINAL DESIGN INTENT:
   - The decoy values weren't arbitrary - they served a purpose
   - Removing them without understanding why they existed caused failures
   - "Minimalist" isn't always better if it breaks assumptions

2. MODE SELECTION IS COMPLEX:
   - PSB doesn't just look at "last register written"
   - It considers ALL register values as a complete configuration
   - Zero values can be interpreted differently than moderate values

3. CODE ASSUMPTIONS MATTER:
   - Battery_GoToVoltage() assumes decoys exist (line 142 comment)
   - Initialization must establish these assumptions
   - Breaking assumptions causes subtle, hard-to-debug failures

4. DEBUGGING REQUIRES COMPLETE CONTEXT:
   - Understanding the FULL configuration state was key
   - Register dumps at multiple points revealed the pattern
   - Comparing working discharge vs failing charge showed the missing piece

5. TEST ALL PHASES:
   - Testing only Phase 3 would have missed Phase 4 discharge showing decoy usage
   - Complete experiment runs reveal dependencies between phases
   - Integration issues don't show up in isolated tests
